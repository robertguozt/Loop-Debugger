A debugging loop that runs your tests, not its imagination.

Point it at a failing pytest target. It spawns an isolated pod, reproduces the failure, reads the frames in the traceback, applies one minimal patch, and re-runs the suite. It cannot claim a fix it has not watched pass. The interesting part is not the loop, which is forty lines. It is the harness around it.

How the loop works

run_debug_cycle posts the transcript to the Messages API, pulls tool_use blocks out of the response, runs the matching Python function, and returns tool_result blocks in the next user turn. That repeats until the model calls report_resolution or the step budget runs out.

The four phases

The system prompt splits the work and the agent announces which phase it is in before each call. Two rules do the heavy lifting: it may not name a root cause before a failure appears in tool output, and it may not claim success before a passing run appears in tool output.

1 · Reproduce

Create the sandbox, run the target, capture the traceback and the exit code. No guessing ahead of the evidence.

2 · Localize

Read the frames named in the traceback. Follow imports and call sites. State the observed value and the expected one.

3 · Patch

One sentence of root cause, then the smallest edit that fixes it. One defect per patch, and no refactoring.

4 · Verify

Re-run the target, then the full suite. A still-failing run restarts at phase 1 with the new output as evidence.

After three patches without a passing run, the loop injects a message telling the model to stop editing and widen its search. Stacked patches on a wrong hypothesis are how these agents usually go off the rails.

The tools the model sees

TOOL_SCHEMAS in tools.py goes to the API verbatim. ToolBox holds the mutable session state and dispatches each block to a typed implementation. A tool that raises returns an error tool_result rather than killing the run, so the model can read the failure and adjust.

Quickstart

The bundled example needs no API key and no cluster. It still drives the real loop, the real tools, and a real sandbox.

git clone https://github.com/robertguozt/Loop-Debugger
cd Loop-Debugger
pip install -e ".[dev]"

python examples/run_example.py            # scripted model, local sandbox
python examples/run_example.py --live     # real model, local sandbox
python examples/run_example.py --live --k8s   # real model, Kubernetes sandbox

Against your own repository:

export ANTHROPIC_API_KEY=sk-ant-...
kubectl apply -f k8s/

loopdbg --repo /path/to/project \
            --target tests/test_thing.py \
            --namespace debug-agent --revert -v

--revert undoes the agent's edits before it exits and prints the diff. Use it the first few times you point this at something you care about.

The example run

examples/broken_project ships a small statistics library where calc.stats.median returns the upper middle element of an even-sized sample instead of the mean of the central pair. Two of eight tests fail.

1reproduceokcreate_ephemeral_debug_pod image=python:3.11-slim
2reproduceokrun_test_suite VERDICT: FAIL — 2 failing, 6 passing
3localizeoksearch_codebase /def median/
4localizeokread_file calc/stats.py:20-34
5patchokapply_unified_diff_or_patch calc/stats.py −1/+3
6verifyokrun_test_suite VERDICT: PASS — 8 passed
7verifyokcleanup_pod
8done•report_resolution resolved=true

Root cause, in the agent's words: median returned ordered[len(ordered) // 2] for every sample size, so an even-sized sample yielded the upper central value instead of the mean of the two central values. The diff it produced:

+++ b/calc/stats.py
@@ -25,7 +25,9 @@

Inside the cluster

KubernetesExecutor talks to CoreV1Api and makes four calls: create the pod, read it while waiting for Ready, exec into it, delete it. Commands go through stream(api.connect_get_namespaced_pod_exec, ...) with _preload_content=False, and the exit status comes off the error channel. Source arrives as a tar stream written to the exec stdin. 

k8s/00-namespace.yaml     namespace (restricted PSS) + two service accounts
k8s/10-rbac.yaml          Role + RoleBinding for the runner
k8s/20-network-policy.yaml sandbox egress: DNS only
k8s/30-quota.yaml         ResourceQuota + LimitRange
k8s/40-runner-job.yaml    the runner Job and its secret

The Role grants what executors.py actually calls, and stops there:

rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "create", "delete"]
  - apiGroups: [""]
    resources: ["pods/exec"]
    verbs: ["get", "create"]

Guard rails

  • Path containment. Every path resolves against the repository root, and anything outside it raises before the read or write.
  • Patch validation. The snippet must match exactly once, and a patch that would break ast.parse is rejected instead of written.
  • Image allowlist. The image name arrives from the model, so it checks against a prefix list before any pull.
  • Sandbox hardening. No service account token, all capabilities dropped, UID 1000, RuntimeDefault seccomp, egress denied except DNS.
  • Bounded blast radius. A ResourceQuota caps pods and CPU, and the executor deletes its pod from a finally block even when the model crashes the loop.
